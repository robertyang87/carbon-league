## 1. 结论

**“高手回放模仿学习 → 带历史对手的自我对弈强化学习”总体合理；当前实现和实验设计尚不足以可靠判断具体训练改动的效果，也不足以宣告模仿学习已到天花板。**

这个项目已经具备可工作的策略架构、快速模拟器、多教师数据管线、PPO 训练器、对手池、打包工具和较丰富的实验记录。当前首要问题是：训练目标、实际运行参数、本地比赛规则、上线策略以及验收口径没有完全对齐。继续扩大算力，会把这些偏差一并放大。

建议保留现有 BC→RL 主线，先修复实验可信度，再用少量、可归因的对照实验选择奖励、温度、对手池和模型容量。搜索可以作为候选工具，但目前没有证据支持“剩树多就说明 BC 学不会，必须搜索”的推论。

## 3. 最重要的问题：训练方式是否合理

### 3.1 哪些部分合理，值得保留

**先模仿再强化学习，适合这个游戏的样本成本。** 从头随机探索要同时学招募、采集、回库、种树、避碰、争夺和终局，稀疏有效行为很难获得。高手回放能提供可用起点；RL 再用实际收益修正教师偏差和学生自身分布中的错误，这个顺序合理。

**CNet2 的表示与游戏结构基本相符。** 循环卷积对应 15×15 环形地图；棋盘特征、单位历史、单位间注意力和顺序动作解码，有助于表达部分可见信息、单位协作、共享现金与空间冲突。没有必要仅因暂时涨分慢就推翻架构。

**当前 PPO 的基本结构有合理依据。** 对自回归联合动作，按单位条件概率求和得到联合 log-prob，再构造 PPO ratio，符合该策略的概率分解；价值网络、GAE、参考 BC 策略的 KL、历史快照和对强手加权采样，都有各自用途。它们是可验证的设计选择，不是“配置上存在就必然有效”。

**多教师和历史快照值得保留。** 它们能改善覆盖与减少自我对弈遗忘。多教师共享主干仍可能产生负迁移；教师文件多、快照多，也不自动等于打法多样。

**已有一些正确的数据纪律。** 常规 builder 按完整对局 ID 划分 train/val，双方样本留在同一侧；回放 `order` 身份映射与 `obs[t] → action[t+1]` 对齐方向正确。检查到的 `full_carbon` 用作训练辅助监督，策略输入仍来自各方实际观测，未发现它直接造成完整碳图推理泄漏。新重标路线另有 R06 所述问题。

### 3.2 当前奖励并不等价于只优化终局现金

来源：[奖励计算][ppo-reward]、[资产估值与 rollout][rollout-worth]、[正式训练配方][plan-path]。

当前支持 `dense / terminal / worth`；正式配方使用 `--reward worth`。`worth` 包括现金、工人携带碳以及树的估计剩余价值，其增量构成每步奖励的主体。`game_rewards` 还会乘奖励尺度、加入终局胜负奖励（默认 `win_bonus=0.1`），并可叠加退火的存碳/损失塑形（默认系数为0）。以下公式专门讨论 worth 增量项；反例两条轨迹终局相同，胜负奖励也相同，不改变结论。代码默认 `gamma=0.995`，配方没有显式覆盖这一值。

设 `W_t` 为第 t 步资产分差，`r_t=W_(t+1)-W_t`。**不折扣**求和时确实望远镜相消为 `W_T-W_0`，但折扣后：

```text
Σ[t=0..T-1] γ^t (W_(t+1) - W_t)
= -W_0 + γ^(T-1) W_T + (1-γ) Σ[t=1..T-1] γ^(t-1) W_t
```

最后一项额外奖励中间的资产占有。因此“终局现金相同”不保证“训练回报相同”。数学反例：T=300、γ=.995，一条资产轨迹从 0 升至 1000，中间保持，末步回到 0；另一条始终为 0。二者终局相同，前者折扣增量回报约 **776.59**，乘配方的 `3.33e-4` 后约 **0.2586**。这是目标不等价的数学反例，不是已复现的可达游戏刷分策略。

这不证明 `worth` 一定比终局奖励弱：它可能改善学习信号。但不能将它当作不改变目标的纯信用分配技巧，树估值误差也可能被策略利用。`dense` 的折扣现金增量同样偏好更早的现金积累。

**建议：**先明确基础目标是终局分差、胜负还是与平台软分一致的组合；再比较当前奖励与一个明确对齐终局目标的基线。若使用 potential shaping，应以明确的基础奖励加 `γΦ(s_next)-Φ(s)`，终止状态势函数归零；这保证的是相对于既定折扣基础目标的性质。不要只给当前 `Δworth` 加上“potential-based”名称。有限时长下 `gamma=1` 是可测试选项，稳定性仍须验证，不能直接宣布更优。

### 3.3 训练和实际比赛存在三层差异

1. **环境差异已确认。** PPO rollout 也固定 `range(1,301)`，且缺少灭绝终止。R01/R02 不仅影响考试，也影响训练轨迹、奖励和价值目标；修复应同时覆盖 rollout、eval 和搜索。
2. **出招差异需要实测。** 训练按概率抽样，考试和主流纯网包多用贪心；上线包还可能叠保护逻辑及量化。随机训练本身合理，但提升的是采样策略，并不自动保证贪心包提升。要分别测浮点采样、浮点贪心与最终打包策略。
3. **对手差异已部分确认。** R04 说明我方降温同时污染快照对手温度；因此过去的温度消融不能直接解释成“只改变了我方探索”。修复后分别配置 learner、SELF 和 SNAP。

应建立同权重、同观测、同历史、同温度下 actor 与 learner 重算 log-prob 的一致性检查，并记录训练策略与最终包的动作差异。量化和保护导致的差异可以是有意设计，但必须可测、可解释。

### 3.4 价值网络、KL 和异步采样需要诊断，不能凭名称认定有效

- 价值输出为 tanh，训练对 return 裁剪到 `[-1,1]`，但 GAE 使用原始缩放奖励。在 `rscale=3.33e-4` 等配置下，大分差回报可能超出此范围。**应记录 return 裁剪比例、预测饱和比例、解释方差及分阶段误差**，再决定扩大输出范围、重标度或改变目标；目前没有证据证明所有训练已经因饱和失败。[源码][ppo-update]
- BC KL 能防止已学行为迅速崩坏，但过强可能限制改进。R03 已使一项“放松 KL”的实验实际未生效，应先修实现，再测约束强度。
- 默认允许边采样边更新，行为策略可落后一轮；保存 behavior log-prob 和 PPO ratio 是必要条件，但不能代替策略滞后诊断。检查按版本差分组的 ratio、clipfrac、有效样本量与收益；小规模同步基线有助于区分算法与吞吐优化问题。
- `--ratio unit` 是不同于联合 ratio 的近似选择；当前默认 joint 与自回归概率分解相符。不能把不同选择混为同一实验。

这些是应补诊断的方法风险，不应在没有原始分布证据时断言“价值网络已失效”或“PPO 公式整体错误”。

### 3.5 对手池的有效多样性，比快照文件数量重要

对 `reports/live/snipe.jsonl` 第 36–75 轮的历史窗口汇总，记录了 182,727 条轨迹：SELF 约 24.88%、自家历史快照约 48.96%、W1 约 17.93%、W2 约 8.23%。**SELF 一局两侧都会入账，这不是独立对局占比；也不代表后来 n1 池仍是该配置。**

这一窗口说明，大部分训练来自自家谱系和少数替身。它能产生进步，也可能只学会利用这几个替身的弱点。应按实际行为与交叉对战结果评估多样性：抢树压迫、采集回库、基地口争夺、终局转换等，而不是仅按模型名称统计。

建议明确三个集合：训练池、用于选 checkpoint 和调参的开发考官、只在候选冻结后使用的最终确认集。公开源码不进训练是有价值的约束，但一个反复用于挑模型、调池的考官仍会间接影响训练决策，不能无限期称为独立测试。

### 3.6 模仿准确率 0.87 不是方法天花板的证据

BC 的逐动作准确率混合了大量普通动作、少量高价值决策、教师随机性和可能未被输入表达的历史信息。它既不等于联合动作成功率，也不等于闭环比赛强度。教师若在同类局面随机选择多个合理动作，准确率可能天然无法逼近 1。

因此，不能由少量版本的 val 平台期推出“数据已经够了、BC 学不会、只能搜索”。应检查分阶段/单位/关键事件的交叉熵与错误分布，及学生自身轨迹上的失败局面，而不是只追一个整体准确率。

“模仿只能跟上、绝不可能超过教师”也过强。标准 BC 没有直接优化超越教师的目标，但多教师融合、去噪和分布差异都可能带来局部超越；反过来也不保证一定发生。RL 是主动优化收益的一条合理路径，不是由这些记录证明的唯一可能路径。

多教师扩充、增加注意力或放大网络，都应在固定数据和计算预算下与原基线比较。每次同时换教师、模型、温度、池子和奖励，会失去可归因性。

### 3.7 训练建议：保留路线，先做四个验证

| 次序 | 验证 | 成功标准/要回答的问题 |
|---|---|---|
| A | 参数与环境一致性 | resume 后实际 LR/KL、双方温度、最后动作步、灭绝结果与配置/原版一致；内部异常进入失败状态 |
| B | 奖励与价值诊断 | 明确基础目标；记录 shaping 与终局目标的关系、return 裁剪率、价值解释方差；不靠树数量代替胜负 |
| C | 同起点短对照 | 固定代码、数据、训练池、预算，先比较一个单变量；重要结论用多个独立训练随机种子确认 |
| D | 冻结后的发布验证 | 用实际量化包，在未参与选模的新地图/独立考官上确认，再做平台资源限制下的长尾耗时检查 |

样本量应由目标最小提升和观测方差决定；200 或 600 局不是对所有问题都充分的固定答案。比较需要报告独立地图数、配对覆盖率、异常局、均值与不确定性。按有效提升/计算成本判断扩容价值，GPU 占用率高只说明资源忙，不说明训练有效。

## 5. 详细发现与修复验收

### R01 — 对局多走一步

位置：[eval 默认步数][eval-horizon]、[原版终止判断][original-horizon]、[PPO rollout][rollout-loop]、[搜索边界][search-horizon]。

原版最终观测为 step=299，最后一次调用代理时是 step=298，总计 299 次转移。本地默认执行 300 次，PPO rollout 也固定 300 次。搜索 `left=299-step` 已是剩余实际转移数，再使用 `left+1` 会推进到游戏之外。

确定性复现：仅在 obs.step==299 招募，其余步不动作，对手全程空动作。

| 执行方式 | 最后调用 step | 最终现金 |
|---|---:|---:|
| 原版完整 env.run | 298 | 80 : 80 |
| 本地 299 次转移 | 298 | 80 : 80 |
| 当前默认 300 次转移 | 299 | 50 : 80 |

额外一步可以改变存碳、碰撞、招募和树收入，尤其影响末段改动与小分差晋升。修复应统一 runner、训练和搜索的剩余步数定义；验收须比较代理最后收到的观测、终止状态和最终奖励，不能只比较 Board.next。修复后重跑相关边界候选，不能直接把既有所有成绩宣告作废或全部有效。

### R02 — 灭绝后仍继续，已输局可能被记为赢

位置：[原版灭绝规则][original-elimination]、[本地比赛循环][eval-loop]、[PPO rollout][rollout-loop]。

原版对“无工人、无树且无法招募”的一方立即结束并给负奖励。FastCarbon 主要实现 Board 转移，本身不承担完整环境生命周期；当前调用方没有补上该规则，只统计 bankrupt_steps 并继续到固定步数。

最小局面：step9，A现金20且无工人无树，B现金10且有采集员。下一步原版返回 A `DONE/-291`、B `DONE/10`；FastCarbon现金仍为 `[20,10]`，现金判胜会得出相反结论。

修复应在公共 runner 中统一 done/reward，rollout 提前终止并正确处理 GAE 的终止边界，搜索也应识别灭绝。验收覆盖单方灭绝、双方异常/结束和正常到时，避免把正常现金、奖励编码和统计胜负混成一个字段。

### R03 — 续训参数被 checkpoint 覆盖

位置：[rl2_ppo_train.py:261][ppo-resume]；历史证据：[snipe.jsonl:55][snipe-log]。

optimizer 按 CLI 新值创建后又执行 load_state_dict，恢复旧学习率；kl_coef 也由 checkpoint 覆盖。后续可选 KL 自适应不等于应用新的 CLI --kl，代码没有在恢复后重新设置 CLI LR/KL。

```text
requested_lr=3e-5   effective_lr=1e-5
requested_kl=0.025  effective_kl=0.1
```

历史记录声称第24轮后 KL 0.1→0.05，但第36–75轮共40条日志全部为0.1。这与代码行为一致，不能据此实验判断降低KL的效果。独立价值优化器的 --vlr 也受同类恢复影响。

修复时区分“未指定，继承检查点”和“显式指定，覆盖”；恢复后写入实际参数清单。验收覆盖无resume、只继承、明确覆盖，以及策略/价值两套optimizer。证据：[resume-output.jsonl](review_evidence/20261112/resume-output.jsonl)。

### R04 — 对手温度被全局我方配置覆盖

位置：[actor decoder][actor-temperature]、[快照调用点][snapshot-temperature]。

全局 TEMP_KIND 存在时，decoder不再使用传入temp。learner和snapshot复用同类actor，导致 RL2_SNAP_TEMP 的正温度值失去预期作用（仍可能控制greedy开关）。

设置 CNET2_TEMP_KIND=0.15,0.3,0.3，对相同collector logits分别传入0.5、0.7、1.0，实际动作概率均为：

```text
[0.035060, 0.068288, 0.133007, 0.259062, 0.504583]
```

这直接破坏我方降温实验的单变量解释。应按actor实例配置温度；验证不同对手温度确实产生不同概率，并验证训练log-prob与采样一致。不能仅凭这一bug断言它解释了全部训练停滞。证据：[temperature-output.jsonl](review_evidence/20261112/temperature-output.jsonl)。

### R05 — 异常策略通过考试完成门

位置：[根推理fallback][root-fallback]、[bigeval汇总与退出条件][bigeval-gate]。

根推理失败被捕获为root_errors并返回{}；eval已累计到a_errors，但bigeval先保存summary，之后才添加search_error_games，该字段未进入已保存结果。内部错误仅打印warning；退出条件只检查外层error与缺局。

本次以已有b128权重、当前打包工具构造纯网包，注入非法TEACHER=999。两局各执行两步，根推理均失败，仍得到n=2、err=0、进程退出码0，同时stderr另有WARN_SEARCH_ERRORS=2。

这是故障注入，不表示线上Echo2的teacher配错。它说明即使检查exit code和err=0，仍无法证明考试执行了预期策略。先汇总健康状态再落盘；内部错误必须进入失败门；保留首个异常堆栈，配对分析也应拒绝或显式标记异常实验，不能静默只取有margin的局。证据：[真实故障包汇总](review_evidence/20261112/runtime-fault-gate-summary.jsonl)。

### R06 — 重标打破原始对局的训练/验证隔离

位置：[lb_relabel遍历语料][lb-relabel]、[merge_dagger重新划分][merge-dagger]、[计划强制改train][lb-split-plan]。

lb_relabel没有按原meta排除验证局；派生shard被加前缀/改后缀，merge按新名字CRC重新分配。计划又要求全部重标局置train，以保持base val原样。但验证集文件不动，不代表相同状态没进入训练。

真实dry-run对局 `0efcfa1227b59fd7f89ee0c9b9ca9268-1.json.gz`：原key按builder规则CRC32%10=0（VAL）；派生名 `lb_cp_0efcfa1227b59fd7f89ee0c9b9ca9268-1.npz` 的余数为5（TRAIN）。

该专家迭代线尚标为预置、未立项；未证实已发布模型受污染。修复要求记录original_game_id并继承split，或只重标原train。验收应按原始对局ID及状态来源检查交集，而不只检查文件名。对纯新生成的独立对局，可采用自己的分组划分规则。

### R07 — 当步招募死亡漏记，入库账本出现负数

位置：[eval_v53账本重建][eval-ledger]。

通过pre/post新出现且存活的ID识别招募，会漏掉当步招募、当步碰撞死亡的工人。随后现金差倒推存碳，把漏记支出算成负入库。

两次在同一基地招募、旧单位不移动：实际招募2人花60、死亡2人、入库0；账本为招募1人花30、死亡1人、入库−30。总现金仍正确，但用于解释失败机制的账本错误。

应使用模拟器事件或明确计数记录招募、死亡、存碳；验收覆盖基地堵塞、新招募撞敌和同方碰撞。不要将同一现金差同时充当事实记录和分类账的唯一来源。

### R08 — 数据分片缓存与配置脱钩

位置：[cnet2_build.py:262][build-cache]。

缓存只依赖回放名（weighted模式还含side），不含教师映射、STEP_MIN/MAX或特征版本；存在即复用，而meta按新配置重写。

真实builder合成输入复现：第一次输出step=[0,1,2]、teacher=[0,0,0]；将STEP_MIN设为2且交换教师0/1行后重建同目录，数组仍保持旧值，metadata却声称新映射。预期应为step=[2]、teacher=[1]。合成fixture在index中使用足够步数以穿过扫描门，实际仅含三条决策，目的是隔离缓存行为，不代表合法完整天梯回放。

修复需缓存配置指纹及来源hash，不匹配即重建或明确拒绝。未证明现有Echo数据已经因此污染。证据：[cache-output.jsonl](review_evidence/20261112/cache-output.jsonl)。

### R09 — “终局剩树少”没有被证明是应优化的主指标

位置：[replica_gap_plan.md:35][tree-plan]、[专家迭代验收][lb-acceptance]。

方案由替身终局6.8棵、教师2.1棵，推导“自己的树没清完”，再要求降至≤4.5。原版动作只有移动和招募，没有卖树或主动清算树资产；树每步吸碳入现金，达到50步寿命后枯萎释放格碳，或被对手种植员夺走。释放格碳还需采集并运回才转为现金。

终局剩树少可以来自更早种树、少种、到龄枯萎或被抢。还活着的树可能早已回本。教师天梯混合对手与替身固定考官也不是严格同场对照。

因此残树数可作诊断，不能独立升级为胜负代理，也不能证明BC无能为力。应检查最后50步各笔投入、树龄/取得时间、实际后续收入与最终现金，并在相同对手和地图下比较。可以预注册新假设，但不能把未经验证的归因写成已经坐实的机制。

### R10 — 终局指标将单方增长与分差增长混用

位置：[母本数据][tree-plan]与[新主指标][lb-acceptance]。

母本记录教师末段现金+2093、对手+1391；新方案却要求 `(终局双方分差 − step270双方分差)` 向+2093靠拢。对应同组数字应为 **2093−1391=702**，不是2093。

应统一双方、时间点、现金/奖励口径，再算教师和候选基线。R01修复后还需重新核实所谓“最后30步”的实际转移区间。该错误会影响新方案是否过线，不能用改阈值掩盖口径错误。

### R11 — 纯网络计时工具在总结阶段崩溃

位置：[cnet2_search_timing.py:27][timing]。

SEARCH=False时SIMS为空，但脚本无条件对其求percentile。合法b128纯网包完整执行300步后，摘要抛出 `IndexError: index -1 is out of bounds for axis 0 with size 0`，退出码1，已收集的wall p99/max也没有完整输出。

通用耗时应先输出；未搜索时searched=0，搜索分位数为null。同时汇总root_errors，且跟随R01修正对局边界。该故障不能被解释成策略本身运行超时。

### R12 — TTA与guard复用不同坐标系的编码

位置：[TTA编码][tta-encode]、[guard重解码][guard-cache]。

TTA按多个对称视图编码，CachePolicy最后保存最后一个变换视图；guard却可能拿该编码配原始x/aux重解码。b128权重上TTA=2后的缓存与原坐标编码最大差0.58738，明显不是舍入噪声。

触发条件是TTA=2/4且guard进入相关改动分支。未确认线上Echo2启用组合，也未证明具体胜负损失。修复应在guard保留完整TTA解码路径或缓存原始坐标编码，并用强制触发guard的对称场景验证动作等变性。

### R13 — 自动采集仍写入已退休分支

位置：[ladder-replay-pull workflow][replay-workflow]、[live操作说明][live-readme]。

基准HEAD说明已将旧分支后续提交合入main，并按所有者要求退休cnet2-search-v12；workflow仍固定checkout该分支，pull/rebase也指向它。live说明同样要求往旧分支推送。

旧分支尚存在时可能继续成功写入，造成main与新回放分离；将来删除时则失败。应统一工作流与操作入口，并以实际新提交所在分支验收，不能只看job绿灯。

### R14 — 接手入口过时，最新制品不能仅靠本仓复现

位置：[README][repo-readme]、[HANDOFF][handoff]、[当前live状态][live-status]。

README仍引导可上传v2，HANDOFF开头仍称最好版本v2/零提交，而该候选文件已不在Git tree中；后段又有v14–v17记录，最新live已是Echo2、n1r等。文档标题日期和内部更新日期也不同。

main未包含最新Echo2/n1r实际权重与完整提交包。它们可能有意存放外部，但当前缺少足够统一、可执行的制品索引，接手者不能凭仓库完成逐字复现。不能将“本次已有b128包测试成功”表述为“线上最新包通过复测”。

建议设唯一CURRENT入口，记录源码SHA、权重hash及可访问位置、打包参数、最终包hash、策略ID、有效训练配置、数据split版本、考试结果路径与状态日期。历史交接明确归档。大权重不必强塞Git，但来源必须可恢复。

### R15 — ECS查询失败被误报为释放验证成功

位置：[ecs_release.py:106][ecs-release]。

预检与DeleteInstance检查HTTP状态，但后续DescribeInstances未检查状态。503/403等错误解析为空列表后，代码将present=False直接视为已释放。

纯本地mock：预检200且实例匹配，删除请求200，下一次查询503，输出仍为：

```text
VERIFY_HTTP=503 PRESENT=False STATUS=None
RESULT=RELEASED_VERIFIED
```

未实际操作云实例。只有查询成功、响应结构有效且目标确实不在列表时，才能确认释放；失败重试超限应返回非零并标明未验证。否则调度可能停止追踪仍在计费的资源。证据：[mock输出](review_evidence/20261112/ecs-release-repro.txt)。
