# vec_selfplay 生成器瓶颈拆账短注（＋成本/排期附注）

**一句话定位**：瓶颈不在 GPU 算力、不在 CPU 核数，在**评估传输形态**——现行 `tools/katago_m3s2/vec_selfplay.py` 是「多 worker 进程各玩一局、每局每步同步阻塞 RPC 到单推理服务器」的结构：每个 worker 同时只有 1 局在飞、1 个未结请求，fast 步每次只送 1 行过 GPU；唯一的推理服务器单进程串行服务全部请求（取到首请求后无等待窗、顺手抓已排队者拼批，上限 256 请求，但可拼的量被在飞请求数封顶），于是 GPU 约 78% 时间无活、worker 约八成时间阻塞在响应队列上；加 worker 只是把队列拉长（每 worker 每局周期 5.97 s→12.18 s），总吞吐被服务器串行服务率封顶。背景实测（作战室给，L20 2026-11-20 02:51，gen1r、**deep-frac 0** 口径）：8 worker 1.34 局/秒、24 worker 与生产批并行争用下 1.97 局/秒，GPU 利用率均约 22%，CPU load 约 2–8/32。一期改造件 `vec_selfplay2.py`（并步池＋整轮拼批单次前向）与等价性闸 `gate_vec2.py` 已随本注交付；vec_selfplay2 是**旁路件**——闸不过即弃置，不开迭代修复循环（所有者 2026-11-20 03:12 定位）。

## 附注：成本/排期（一页）

- **一期代码（本期已交付，非待开发）**：`vec_selfplay2.py`（并步驱动：多局同池并步推进、每轮把全池待评估局面按 tag 拼成一个大批量单次前向、每局独立 RNG 流（种子＝--seed＋1000003×局号，与现行同派生）、落盘 schema 与现行逐字一致；逐步模拟逻辑自现行文件移植、只换传输层）＋`gate_vec2.py`（等价性闸，见下记录位）。本机自检：py_compile 通过；schema 常量与现行 write_shard 逐字比对一致；并步调度器纯 numpy 桩测通过（跨局拼批、结果按行路由逐行对参考值断言、池补充）；移植函数归一化 diff 只剩签名/注释差。真跑（torch/GPU）在 L20。
- **后续人日（估计）**：服务器侧计数器仪器化（实测 boards/批量分布，消掉上表最大不确定性）≈0.5 人日；如闸通过后要并入生产 loop（run_loop.sh 接线＋回归）≈1 人日。
- **验证时长（估计）**：闸 (a) 固定批前向一致性分钟级；(b) 200 局同种子对照 fast 口径新旧各约 2–3 分钟、deep 口径按 ≈40,000 行/局另计（旧件 deep 吞吐未实测）；含判读半天内。
- **改造后吞吐估计（估计，推导：大批量前向 0.004–0.071 ms/行（NETEXP 锚区间）×每局行数，与 CPU 模拟侧 ~0.5–1.1 CPU-s/局 ÷ 32 核，两边取 binding 并留组装/IPC 余量）**：fast 口径 **8–15 局/秒**（现 1.34–1.97），GPU 利用率目标 **≥60%**；deep 口径 **0.5–2 局/秒**（现 deep 未实测；受 boards 不确定性主导）。
- **Gen-3 排期影响（估计）**：8,000 局 fast 口径生成 68–99 分钟 → **9–17 分钟**；deep 段按上行另算。若 Gen-3 生成等闸结论，等待项＝L20 闸跑＋判读（半天量级），非开发阻塞。
- **与 NETEXP 加深 +2 叠加再估（估计）**：前向 ×1.317 ⇒ GPU 受限段吞吐 ÷1.317：fast 目标 **6–11 局/秒**、deep **0.4–1.5 局/秒**；GPU 利用率目标不变（≥60%，因 CPU 模拟侧更早成为 binding）；每局调用结构不变（步数/席位由底盘钉死，与网络深度无关）。
