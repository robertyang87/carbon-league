在付款臂第 272 步，本方采集工 41 在格 15，载货 170.0，向右进入格 16；对手 27 同时向下离开格 16。两者没有在同一落点相遇。暂缓臂第 277 步也出现了同时移动的防守局面，对手采集工 57 从格 168 向上进入格 153，本方 9 同时向右离开格 153，带货兑现。两例都能直接看到有工人逼近货运路线；回放无法确定其内部意图，亦未测试换一步能否截获。

## 怎样复核与使用

从本目录运行 `OPENBLAS_NUM_THREADS=1 python analyze.py`，使用仓内该项目的 Python 环境。程序从发布的选择清单校验根、原始轨迹与两臂命令带摘要，在每个联合步对照官方解释器与带收支分类的 FastCarbon 余额，在终局核对双方官方分数。根后各步差之和须以分为单位等于官方终局分差标签。只重放已保存的命令，不调用参赛策略。[程序](analyze.py) · [两臂标签的生成与校验](../label.py)

`turns.json.gz` 每个根的 `contexts.pay/defer` 以实际步号索引峰值与前 3、5、10 步。`public_before_order` 含双方公开的现金、基地、工号、坐标、载货、角色、树和两个物理席各自可见的碳格索引及读数。单席查询应只取该席的碳视野。配套的 `actual_joint_orders` 是当步真实执行的命令，工人缺省命令为原地停留；`cash_events` 是发令后才出现的账目。事件前 3 项为渠道、入账/支出席和带符号金额，后续项识别相关工人、格子、基地或树。峰值、两臂差和未来得分均是事后诊断。训练时若使用提前可见的运货线索，应从普通决策根采样，仅给策略当时该席的信息；用事后选出的峰值窗口当作无偏样本会夸大大额交货的频率。[完整逐根数据](turns.json.gz)
