# 拆账短注：train.py 喂数瓶颈与 train2 并行喂数（旁路件，闸不过即弃置）

依据：现行 `tools/katago_m3s2/train.py` 逐字直读（仓 main，md5 `34898e7c0132b1834404bff01f0cde21`，341 行）；实测锚为作战室给 L20 Gen-2 读数：主进程单核 CPU 100%、GPU 39–57%、显存 1.6/46 GB、步速 11.78 步/秒。L20 32 核现只用 1 核。

## 1. 现行喂数路径的串行点（逐项，全部在主进程、与训练步串行交错）

每步（batch 512）在 GPU 计算之前，主进程单线程依次做：

1. **索引与增广抽签**：`order[s0:s0+512]` 切片 + 逐行 `int(rng.randint(4))`（512 次 Python 级调用）。
2. **逐行增广物化**：`[augment(rows[i], g) for i in idx]`——512 次 dict 构造 + V4 fancy-index 拷贝（x 的 54×225 平面重排、tw/tb/mask/carbon 索引拷贝）。
3. **逐键堆叠与类型转换**：11 个键各一次 `np.stack`（512 行拼接拷贝）+ `.astype(np.float32)`；x 还要 `/100.0`，aux_delta `/1000`，carbon `/100`，margin 过 `score_utility`（tanh/clip）。单步原始数据量 ≈ 512 行 × 28,841 B/行 ≈ 14.8 MB（栈式存储口径），float32 化后仅 x 一键即 512×54×225×4 B ≈ 24.9 MB。
4. **逐张量同步拷贝上 GPU**：11 个张量逐个 `torch.from_numpy(...)` 后逐个 `.to(device)`——**无 pin_memory、无 non_blocking**，H2D 与第 2–3 项及 GPU 计算全串行，GPU 在喂数期间只能空转等。
5. 训练步本身（BF16 autocast 前向/反向/AdamW）排在以上全部之后；日志每 200 步打印步速，无分段计时——喂数占比在现行日志里不可分，只能由利用率反推（见 §2）。

数据加载不是瓶颈：`load_dataset` 两遍栈式全读进内存（dirs 序 → shard 排序 → 行序），训练期零磁盘 IO；瓶颈纯在每步的 CPU 物化+同步拷贝。

## 2. 与实测锚的自洽

- 11.78 步/秒 ⇒ 每步总预算 1000/11.78 ≈ **84.9 ms/步**。主进程单核 100% ⇒ 这 84.9 ms 几乎全程有 CPU 活在跑。
- GPU 利用率 39–57% ⇒ GPU 真算时间 ≈ 84.9 × 0.39–0.57 ≈ **33–48 ms/步（反推值）**；其余 ≈ **37–52 ms/步** 是 GPU 在等 CPU 物化与同步拷贝（喂数段）。两段相加与 84.9 ms 自洽。
- 显存 1.6/46 GB：模型约 110 万参数 + batch 512 激活占用小，显存从不是约束——约束是单核喂数，不是容量也不是算力总量。

## 3. train2 如何逐项拆掉

| 串行点 | train2 处置 |
|---|---|
| ① 索引/抽签 | **留在主进程、逐字同序**：每 epoch 先 `rng.permutation`，再按批、按 idx 序逐行 `rng.randint(4)`，整 epoch 预生成 (idx, g) 计划。现行是交错生成，但训练步不消费 numpy RNG（torch 独立流），故预生成与交错生成**同序等价**（闸 (a) 逐字验，零容差）。 |
| ②③ 物化/堆叠/转换 | 搬到 `--feed-workers`（默认 8）个 worker 进程并行：worker 只做 augment（用预抽的 g）+ stack/astype/缩放，**不碰任何 RNG**；物化函数与现行内联代码逐行同式。worker 内 BLAS 线程钉 1 防互抢。 |
| 交付顺序 | 预取窗口 `--prefetch`（默认 4 步）+ 按步号重排缓冲：**保序交付**，worker 完成先后不进训练序。 |
| ④ 拷贝 | 主进程 `torch.from_numpy` → `pin_memory()` → `.to(device, non_blocking=True)` 异步拷贝（CPU 目标时不 pin、直拷）。 |
| 训练数学 | 逐字沿用：AdamW、余弦 lr 1.5e-4→3e-5、batch 512、epochs 3、wd 0.01、loss 权重 1.5/0.3/0.2/0.2、BF16 autocast、检查点（source 布局 f16 npz）与日志格式不变。CLI 13 个现行参数默认值逐项对照**全同**（自检脚本比对）；新增仅 `--feed-workers/--prefetch/--compile`。 |

## 4. 改造后步速估计（估计）

- 喂数段 37–52 ms/步在 W 个 worker 下理想摊薄为 (37–52)/W + 主进程 pin+提交残量（约 3–6 ms/步，估计）：W=8 时喂数墙时 ≈ 8–13 ms/步，**低于 GPU 真算 33–48 ms/步**——预取深度 4 足以把喂数完全藏到 GPU 计算背后，binding 转到 **GPU 计算本身**（其次是 H2D 带宽：每步约 60–70 MB float32 张量，PCIe 量级为毫秒级，非 binding）。
- 步速上限 ≈ 1000/(33–48) ≈ **21–30 步/秒**；计入步间气泡与主进程残量，**估计落地 18–26 步/秒，约为现行 11.78 的 1.5–2.2×**，GPU 利用率估计升至 85%+。此为估计，真值以 L20 bench 模式实测为准（Gen-4 窗口排期，不占 Gen-3 链）。

## 5. torch.compile（`--compile`，默认关，闸跑时关）

- 预期作用：本网为 6×96 小网、batch 512 时单步 kernel 数多而单 kernel 小，**kernel 启动开销占比可能可观**，compile 的融合/图捕获有望压 GPU 段 33–48 ms 中的启动间隙——但**该占比未实测（未核）**，不写预期数值。
- 风险：首步编译耗时（分钟级可能）；与 BF16 autocast、动态末批形状（尾批 <512）交互需实测；数值路径可能因融合产生与未编译版的浮点级差异——故默认关、闸 (b) 在关闭态下跑，开启须另行单独验，不与喂数改造同批归因。
