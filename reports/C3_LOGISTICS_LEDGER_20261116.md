## RL 卡住定案（2026-11-08 11:16，Mac 侧实测）

- 根因：**不是死锁，是参数更新（梯度步）在云 CPU 上极慢**。实测每组 8 局 + 一次更新：
  云 CPU 24 线程做更新 ≈ 5 决策/秒（2400 决策用 453 秒）；1 线程 600+ 秒未完（已停）；
  Mac GPU ≈ 116 决策/秒，快约 20 倍。自我对弈在云上反而快（64 核并行）。
- 与控制台时间线互证：10:02–10:09 全核突发 = 对弈阶段；10:10 起单核平台 =
  主进程独自做参数更新、worker 闲置等更新结束，一轮迟迟不闭环，看起来像卡死。
- 新分工（定版）：**云上只打对局 + 评测筛选，Mac GPU 做参数更新**。每轮：
  云 52 核打 ~100 局（~3 分钟）→ 数据压缩回传 Mac（~100 MB/轮，出流量
  ~1 GB/小时 ≈ ¥1/小时）→ Mac 更新（4–5 分钟）→ 新权重推云。约 5–8 分钟/轮、
  ~1000 局/小时（原 Mac 单机 <200 局/小时，提速 5–6 倍）。
- 代码改造：训练脚本拆「打对局 / 更新参数」两程序、文件交换，约 2–3 小时（Mac 侧）；
  期间 b128v6 正在 Mac 训练（数据集 v6：1223 局 / 42.9 万决策，Godslayer 409 局、
  Top3 338 局，未用 WB 与 v7；5 轮 × 12–15 分钟），训完先在云上跑筛选（几分钟）。
- 对云主机的影响：角色收窄为对局生成 + 筛选；改造与 v6 训练期间基本闲置，
  但 ¥2.58/时量级不值得为几小时空转释放重开；整夜闲置才考虑释放。

  M 区 c16g1 ¥3.63769/时（释放率 ≥10%）、c32g1 ¥4.762905/时（5–10%）、
  c56g1 ¥7.64155/时（0–3%，最大单卡，56vCPU）、双卡 c32g1.16xlarge ¥9.42081/时。
  **无 64vCPU 单卡 A10**；gn7i 的 vCPU 是超线程（物理核 = vCPU/2）。
- 效率模型（每轮 100 局 = 对局段 + 传输段 + 更新段 3 万决策）：对局 52 核约 3 分钟
  按物理核线性折算；更新 Mac MPS 实测 116/秒 ≈ 4.3 分钟，A10 估 2–4 倍 ≈ 1.1–2.2 分钟。
- 结论（每万局成本口径）：**双机 c8y（¥2.58）+ c16g1 抢占 M 区（¥3.64）= ¥6.22/时**，
  约 1110–1400 局/小时、约 ¥50/万局，Mac 解放——首选。同地域跨可用区（N↔M）
  仍可同 VPC 内网互通、传输免费。备选：c16g1 按量 N 区（合计 ¥12.78/时）无回收风险。
  一体机各档因物理核减半，每万局成本（¥85+）均劣于现状分工（约 ¥35–47/万局）。
