# 技术路径和执行计划：纯策略网络加自我对弈（2026-11-11 晚起）

本文取代 `reports/plan_20261111_pm.md` 里的三线安排。用户已认可路径；时间不是约束，每一层用实测结果决定下一层投不投。

代码分支 `cnet2-search-v12`，要求 `77e3ce0` 或更新。每台机器开跑前核对提交号和包的 md5；进程数用 `nproc --all`。

## 0. 路径和依据

**主线：纯策略网络，模仿起步，然后大规模自我对弈强化学习。搜索和模仿降为辅助。**

| 实测 | 数字 | 结论 |
|---|---|---|
| Master2 公开源码 | 纯网络、不搜索、模仿起步后自我对弈、按概率抽样走子 | 这条路在这个游戏上走得通 |
| 搜索对替身 / 对 Master2 真身 | +318 ± 56 / +57 ± 74 | 搜索的收益主要来自替身走子可预测 |
| 把搜索训回网络 | 学会 1 个弄坏 1.3–4.6 个，四种做法同一条曲线 | 搜索不是好老师 |
| 规则旋钮、整局加权、单决定分叉 | 全部为零或负 | 现有打法是局部最优 |
| 模仿 Master3s（43 局） | 只教种植员 +28 ± 39；加招募 −173 ± 40；车的一致率约 0.85 | 模仿最多跟上，不能超过 |
| 我们以前的自我对弈 | 每轮 32–96 局，共一两千局 | 规模小了一百倍，没有真正试过 |

**三层，后一层由前一层的结果决定：**

| 层 | 内容 | 要回答的问题 |
|---|---|---|
| 一 | 现有网络加现成训练器，自我对弈放大一百倍 | 自我对弈在我们手里能不能涨分 |
| 二 | 不换网络，改造造局引擎：卷积集中到 GPU 批量算，自己打自己两边都记录（见第 3 节） | 同样的机器能不能多造十倍以上的局 |
| 三 | 新引擎上持续做大规模自我对弈 | 能不能追上并超过 |

第一层和第二层同时开始。第三层在两者都过线后开始。

## 2. 第一层：自我对弈放大一百倍

### 2.1 前哨（Mac Studio，今晚）

目的只有三个：量速度、确认不崩、确认新奖励能用。不看分数。

```bash
cd ~/carbon/code && export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 CNET2_TEACHER=2
python3 rl2_ppo_train.py --adapter cnet2 --init <Grove1 策略网浮点权重> --out ../data/rl3/pilot_a \
    --device mps --workers 14 --lockstep 4 --games 400 --iters 6 --temp 0.7 --reward worth \
    --lr 1e-5 --kl 0.1 --rscale 3.33e-4 --snap-every 5 --eval-every 3 --eval-pairs 16 \
    --eval-opps '<Master2s 替身 v2.py>,<opp_master2r.py>' \
    --pool '[["<Master2s 替身 v2.py>", 1.0], ["<M 风格开局网络.py>", 1.0], ["<Scout1 纯网络.py>", 1.0]]'
```

回报：
1. 每轮对局用时、更新用时（分开报）。
2. `train.jsonl` 每轮的：与参考策略的 KL、价值损失、优势的标准差、平均分差。
3. 镜像局（分差正好为 0）的占比。超过 1% 立刻停并回报。
4. 对局里有没有开局破产、超过 30 个种植员这类异常。

### 2.2 正式运行（L20 加 64 核）

先冒烟：`--games 64 --iters 2`，再量一轮 2000 局的对局用时和更新用时。更新超过 30 分钟就按顺序试 `--mb 1024`、`--epochs 1`，把结果回报后再定。

```bash
python3 rl2_ppo_train.py --adapter cnet2 --init <Grove1 策略网浮点权重> --out ../data/rl3/grove1_a \
    --device cuda --workers 60 --lockstep 4 --games 2000 --temp 0.7 --reward worth \
    --lr 1e-5 --kl 0.1 --rscale 3.33e-4 --snap-every 5 --eval-every 5 --eval-pairs 32 \
    --eval-opps '<Master2s 替身 v2.py>,<opp_master2r.py>' \
    --pool '[["<Master2s 替身 v2.py>", 1.0], ["<M 风格开局网络.py>", 1.0], ["<Scout1 纯网络.py>", 1.0]]'
```

规矩：
- Master2 真身只当考试对手（`--eval-opps`），**不进 `--pool`**，它的对局不进任何训练集。
- 对手池是三个本地对手加自己每 5 轮的快照。
- `CNET2_TEACHER=2` 必须设。

### 2.3 检查点

外部考试都在二十一号机：纯网络，600 对，同种子减 Grove1，对三个训练对手和 `opp_master2r` 分别报。

| 时间点 | 看什么 | 过线 | 不过 |
|---|---|---|---|
| 第 5 轮 | 没有崩 | 自带评测不大幅为负；KL 平稳；无破产 | 停。温度降到 0.5、学习率减半重开一次 |
| 第 15 轮（约 3 万局） | 外部考试 | 对 `opp_master2r` 的分差比 Grove1 高，且超过 2 倍标准误 | 继续到第 30 轮 |
| 第 30 轮（约 6 万局） | 外部考试 | 同上 | 停下来复盘（见 2.4），不加算力 |
| 之后每 15 轮 | 外部考试 | 持续上升 | 连续两次不涨就停 |

每次外部考试同时报账本：招的种植员、每个种植员种的树、树收入、入库、最后 25 步的入库。

**只在替身身上涨、对真身不涨，不算过线。**

### 2.4 第 30 轮不过时按顺序查

1. 价值网络准不准：价值预测和实际回报的相关系数。低于 0.3 说明优势估计基本是噪声，先单独把价值网络训好。
2. 约束是不是太紧：KL 一直贴着 0，说明策略没动，放松 `--kl` 到 0.03。
3. 约束是不是太松：对三个替身涨、对真身跌，说明在钻替身的空子，对手池里自己快照的比重加大。
4. 以上都不是，等第二层的快结构，用十倍的局数再试。

## 3. 第二层：造局引擎改造（2026-11-11 晚修订：不换网络）

### 3.1 实测改变了原来的判断

云端在同一台机器上单进程实测（各打一整局）：

| | 每步耗时 | 说明 |
|---|---|---|
| Master2 真身 | 14 毫秒 | 96 通道、8 个残差块 |
| Grove1 单个网络 | 约 26 毫秒 | 卷积 20、按单位解码 3.6、特征 1.7 |
| Grove1 的考试包 | 45 毫秒 | 包里策略网和推演网各算了一遍主干 |

结论：两种结构只差 2 倍，不是之前说的 10 倍。时间的八成在卷积上，按单位解码不是瓶颈。
换结构最多快 2 倍，还要重新模仿、冒强度下降的风险，**不做**。

真正慢的是训练器造局的方式：每个进程自己用 CPU 算卷积，对手是完整的包。
把卷积集中到 GPU 上批量算以后，每个局面的 CPU 开销只剩特征和解码约 5 毫秒。

### 3.2 已写好的改造

| 改动 | 内容 | 本机核对 |
|---|---|---|
| `code/rl2_ppo_server.py` | 推理服务进程：所有对局进程把一步里的全部局面发过来，合成一批在 GPU 上算主干 | 与原来的结果最大差 3.5e-6 |
| `rl2_ppo_rollout.py` | 同一步里用同一个模型的局面合成一次请求；新对手 `SELF`：当前权重打自己，两边都记录 | 不开服务时与改造前逐步相同（同种子，动作序列的 md5 一致）；两边的奖励之和分别等于正负终局分差 |
| `rl2_ppo_train.py` | `--server 1` 开推理服务；`--self-prior p` 把 `SELF` 加进对手池 | 小规模两轮跑通 |

快照对手也走推理服务。环境变量 `RL2_SNAP_TEMP=0.7`：快照对手按概率抽样走子。
**必须设**：默认是取最大值，对手走子固定，学到的东西会和"搜索只对替身有效"是同一个毛病。

### 3.3 用法（L20 加 64 核；Mac Studio 把 `cuda` 换成 `mps`）

```bash
cd ~/carbon/code && export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 CNET2_TEACHER=2 RL2_SNAP_TEMP=0.7
python3 rl2_ppo_train.py --adapter cnet2 --init <Grove1 策略网浮点权重> --out ../data/rl3/grove1_b \
    --device cuda --server 1 --workers 60 --lockstep 8 --games 2000 --temp 0.7 --reward worth \
    --self-prior 3 --snap-prior 1 --max-snaps 8 \
    --lr 1e-5 --kl 0.1 --rscale 3.33e-4 --snap-every 5 --eval-every 5 --eval-pairs 32 \
    --eval-opps '<Master2s 替身 v2.py>,<opp_master2r.py>' \
    --pool '[["<Master2s 替身 v2.py>", 0.3], ["<M 风格开局网络.py>", 0.3], ["<Scout1 纯网络.py>", 0.3]]'
```

- 对手池的构成：大部分是自己打自己和自己的历史快照，三个替身只占小头（它们是完整的包，每局要十几秒 CPU，占多了会拖慢）。
- `SELF` 的一局产出两条轨迹，`--games 2000` 实际得到的轨迹更多，以 `train.jsonl` 里的 `games` 为准。

### 3.4 第一次运行要量的数（决定后面的规模）

先 `--games 256 --iters 2` 冒烟，再跑一轮 2000 局，回报 `train.jsonl` 的这几项：

| 项 | 含义 | 预期（估计，待实测） |
|---|---|---|
| `games_per_min`、`dec_per_s` | 造局速度 | 每秒几千个局面；2000 局几分钟 |
| `srv.pos_per_fwd`、`srv.t_fwd` | 推理服务每批多少局面、30 秒里算了多久 | 每批几百；`t_fwd` 远小于 30 说明 GPU 有富余 |
| `roll_s`、`upd_s` | 造局和更新各多久 | 造局快了以后更新会变成大头，按 2.2 的顺序调 `--mb`、`--epochs` |
| `pol_s`、`opp_s` | 进程里花在自己和对手上的时间 | `opp_s` 偏大说明替身拖慢，把它们的权重再调低 |

GPU 利用率低而 CPU 满：瓶颈在特征和解码，回报后云端再把解码也搬上 GPU。
GPU 满：设 `RL2_SERVER_AMP=1`（半精度），或把 `--workers` 降一点。

### 3.5 和第一层的关系

- 已经在跑的第一层前哨（旧引擎）不用停，它量的是稳定性。
- 正式运行直接用新引擎（本节的命令），旧引擎的 2.2 作废。检查点规则仍按 2.3。
- 新引擎造局快很多，每轮局数可以在量完速度后加大（目标：每轮造局不超过 10 分钟）。

## 4. 第三层：持续的大规模自我对弈

开始条件：新引擎在 L20 上跑通并量完速度。之后就是同一条命令一直跑，按 2.3 的检查点判断。

- 每轮局数按实测速度定：每轮造局不超过 10 分钟。
- 第 30 轮不过线：按 2.4 的顺序查。
- 换更小更快的网络结构（上榜耗时、容量）留到自我对弈确认能涨分之后再议。

## 8. 一直有效的规矩

- 别人的公开源码只当本地考试对手：不进训练集、不进对手池、不进提交包；`data/public_src/` 不提交。
- 天梯密码不落盘；不合 `main`；上榜和删除条目由用户决定。
- 抢占机随时会被回收：所有长任务可续跑，输出每 10 分钟同步回 Mac。
